# Decisions

Rulings made while building plugbox, in the format
`Ruling: <what> — <why> — <cost if wrong>`.

## Runtime and sandbox

- Ruling: pin `wasmtime = "=50.0.0"` and `wasmtime-wasi = "=50.0.0"` with default features off and only cranelift, component-model, pooling-allocator, wat and backtrace support enabled — the sandbox is only as good as the engine, so the version must be exact and the feature surface small — security fixes need a manual bump; nothing upgrades silently.
- Ruling: enable fuel *and* epoch interruption on every engine, always — fuel is deterministic (good for tests and billing) but only bounds instructions; epochs bound wall-clock time cheaply; together they cover each other's gaps — fuel checks cost throughput on loop-heavy guests (not measured separately here).
- Ruling: one fresh instance per request, no instance reuse across requests — removes a whole class of cross-request and cross-tenant leaks and makes trapped instances harmless; the pooling allocator keeps instantiation in the tens of microseconds — guests cannot keep warm in-memory caches; state must go through KV.
- Ruling: link every capability interface for every plugin and deny at call time with typed errors (never trap, never fail linking) — one binary can run under different grants, and plugins can degrade gracefully — a plugin cannot tell "not granted" from "granted but empty" for `env.get` (both `none`); the WIT documents this.
- Ruling: refuse `wasi:sockets` and `wasi:http` at load time with an import policy, rather than linking stubs that fail — rejected-at-deploy is clearer and safer than failing-at-request; the `sneaky` fixture proves it — any WASI interface we have not listed (for example a future `wasi:keyvalue`) is rejected until the policy is extended.
- Ruling: link `wasi:filesystem` but preopen nothing — Rust's std for `wasm32-wasip2` imports it unconditionally, so refusing it would refuse every Rust plugin; with no preopens every path operation fails — relies on wasmtime-wasi's preopen model being the only way to reach files.
- Ruling: one memory budget across all memories of a component (custom `ResourceLimiter`) instead of per-memory `max_memory_size` alone — a component may contain several core modules, each with its own memory — slightly more bookkeeping on every growth.
- Ruling: reserve exactly `runtime.max_memory` (+64 KiB guard) of virtual address space per memory instead of the 4 GiB default — lets a pool of hundreds of slots fit in a few GiB of address space — bounds checks become explicit instructions, a small per-access cost.
- Ruling: `limits.fuel = 0` means "fuel off for this plugin" (u64::MAX budget), leaving only the deadline — some operators prefer pure wall-clock budgets, and it lets the demo show the epoch path by itself — a misread config could disable fuel unintentionally; the deadline still caps it.
- Ruling: replace wasmtime-wasi's `wasi:clocks/monotonic-clock` with a deadline-capped one (linker shadowing after `add_to_linker_sync`) and report a wait the deadline cut short as `deadline-exceeded`, instead of moving to wasmtime's async API or only documenting the gap (review fix round 1) — fuel and epochs are only checked while wasm runs, so a guest `thread::sleep` blocked the host thread and a server-wide permit for as long as the guest asked (2 s observed under a 50 ms timeout); clock subscriptions are the only pollables a plugbox guest can block on, so capping them closes the gap in ~150 lines without rewriting the sync host — the guarantee depends on that "only blocking pollable" property: linking sockets, `wasi:http` or a real stdin later would reopen it unless those are capped too; guests see a monotonic clock whose zero is the request start and whose resolution is reported as 1 ns.
- Ruling: deadline ticks are `ceil(timeout / tick) + 1` — the store may start late in a tick; the extra tick guarantees the plugin gets at least `timeout` — a plugin may run up to one tick (default 5 ms) past its timeout.
- Ruling: classify a refused memory growth as `memory-limit` even though the guest-visible event is an abort — the operator needs to know *why* the guest aborted; the limiter records the first refusal — if a guest catches the failed growth, then aborts for another reason, it is still reported as `memory-limit`.

## Capabilities

- Ruling: outbound HTTP rejects (rather than normalises) userinfo, percent-escapes in the authority, non-canonical numeric hosts and dot segments — normalisation differences between the checker and the client are the classic allow-list bypass — some legitimate but unusual URLs are refused.
- Ruling: resolve DNS once in the policy layer and hand the vetted addresses to the client, which never resolves again — closes the DNS-rebinding window between check and connect — the client cannot use connection pooling keyed by hostname (it does not pool anyway).
- Ruling: link-local (including 169.254.169.254) is refused even when `allow_private = true` or for IP-literal rules — the metadata service is the highest-value SSRF target and no edge plugin needs it — an operator who really wants it must change code.
- Ruling: the built-in outbound client is plain HTTP/1.1 only; `https://` rules parse but calls return a transport error — adding TLS would pull rustls and a certificate story into a project whose point is the sandbox; the `Upstream` trait is the seam for a TLS client — plugins cannot reach real HTTPS APIs yet (listed in Limitations and the roadmap).
- Ruling: a plugin's implicit KV namespace (its own name) is private; another plugin may not name it, and sharing requires both plugins to set `grants.kv.namespace` explicitly — otherwise any plugin could read another's data by guessing its name — existing configs that joined an implicit namespace must add one explicit line.
- Ruling: KV is an in-process `Mutex<HashMap<namespace, BTreeMap>>` — enough to prove the capability model and quotas, sorted keys give `list-keys` for free — no persistence and one global lock; a real deployment would put a sharded or external store behind the same interface.
- Ruling: guest log messages are truncated to 1 KiB, capped per request, and control characters are escaped — guests must not flood or forge host logs — operators see `\n` instead of real newlines in multi-line guest messages.
- Ruling: guest stdout/stderr go to a capped buffer that silently discards past the cap instead of reporting a closed stream — WASI's in-memory pipe reports "closed" when full, and Rust's `println!` panics on that, which would turn a log flood into a guest abort — the guest cannot detect that output was dropped (the host counts it).

## Server and operations

- Ruling: run guest code on tokio's blocking pool via `spawn_blocking`, with the wasmtime sync API — a guest spinning until its deadline must never stall the async accept loop; sync host functions keep the outbound client simple — one OS thread per concurrent invocation; very high concurrency would want wasmtime's async support and fuel/epoch yielding.
- Ruling: admission control is `try_acquire` on a semaphore (shed with 503), not a queue — a queue in front of a CPU-bound sandbox only adds latency under overload — clients must retry.
- Ruling: separate listener for the admin plane, no authentication, loopback by default — health, metrics and reload are operator tools; authentication belongs in front of them (mTLS proxy, network policy) — exposing `admin_listen` publicly would let anyone trigger reloads.
- Ruling: hot reload is all-or-nothing and serialised — partial reloads produce route tables nobody wrote; serialising avoids two reloads racing — one broken plugin blocks reloading every other plugin until fixed.
- Ruling: file watching by polling (mtime, size) with a two-poll debounce instead of `notify`/FSEvents — no extra dependency, behaves the same on every OS, and tests are deterministic — up to two poll intervals (default 1 s) of reload latency, and a same-size rewrite within one mtime tick could be missed (the admin `POST /reload` is the reliable path).
- Ruling: `[server]` and `[runtime]` changes are not applied on reload, only reported as warnings — listeners and the engine (pool sizing, epoch tick) are built once — operators must restart for those settings.
- Ruling: hand-written Prometheus text exposition instead of the `prometheus` crate — a dozen fixed families, deterministic output for tests, fewer dependencies — no protobuf exposition, no exemplars.
- Ruling: the AOT cache is opt-in and documented as a trusted directory — `Component::deserialize_file` executes whatever machine code the file contains — anyone who can write the directory owns the process; it is off by default.

## Build, tests and benchmarks

- Ruling: guest plugins live in a separate cargo workspace (`plugins/`) built for `wasm32-wasip2`, and `make plugins` copies them to `plugins/dist/` (git-ignored) — host and guest targets cannot share one workspace build — tests require `make plugins` first; `make check` and `make test` do it.
- Ruling: coverage is measured with `cargo llvm-cov --lib --tests`, excluding `src/main.rs` (the CLI is thin glue exercised by `make demo`) with an 80% line gate — the gate should measure the library code that carries the logic — CLI argument handling is not covered by the number.
- Ruling: the benchmark measures the full request path (store, limits, instantiate, call, teardown) in four modes, including on-demand allocation as a control — "pooled vs cold" alone would hide whether the pool or the pre-linking is what helps — numbers are from one loaded laptop and are not a cross-platform claim.
- Ruling: report the measured result that, on macOS arm64, warm pooled instantiation was slower than warm on-demand instantiation, and do not tune the benchmark until it says otherwise — honesty rule; in wasmtime 50 the cheap slot-reset paths are Linux-only (`madvise(MADV_DONTNEED)` decommit, `linear_memory_keep_resident`); on other Unixes a pooled slot is reset by re-`mmap`ing it (`src/runtime/vm/sys/unix/vm.rs::decommit_pages`) — readers on Linux should run `make bench` themselves before deciding on a strategy.
- Ruling: the edition is 2024 and `rust-version = 1.97` — matches the local toolchain and allows let-chains — older toolchains cannot build it.
